# Лабораторная работа № 2 — обоснование темы ВКР

**Автор:** Андрей Алексеев (`pxdkxvan`).

**Рабочая тема ВКР:** проектирование серверной подсистемы сбора, синхронизации и предоставления рыночных данных для аналитической платформы Smart Money Concepts (SMC).

**Личный вклад:** backend и данные: получение котировок и экономических событий, единая временная модель, хранение истории, API для графика и аналитических модулей, выдача данных для Live, Replay и бэктестинга. Формализация SMC-правил, модели машинного обучения и интерфейс разрабатываются другими участниками команды. Конкретные технологии будут выбраны после проверки доступности источников и объёма данных.

**Контекст командного проекта.** Платформа должна объединять свечной график, автоматическую SMC-разметку, экономический календарь, сезонность, объяснимые сигналы и проверку стратегий на истории. Для всех режимов требуется согласованный набор данных. Особенно важно, чтобы исторический запрос возвращал только те версии котировок и событий, которые были доступны к заданному моменту.

## 3. Обзор и сравнение аналогов

### Прямые аналоги

- [QuantConnect LEAN](https://www.quantconnect.com/docs/v2/cloud-platform/backtesting) — движок и платформа для исторического тестирования с подключаемыми рыночными данными. Близок по серверной обработке и повторному запуску алгоритмов. Ориентирован на универсальные стратегии; предметные контракты SMC и формат причин `ALLOW / WAIT / REJECT` для проекта придётся создавать отдельно.
- [TradingView](https://www.tradingview.com/support/solutions/43000562362-what-are-strategies-backtesting-and-forward-testing/) — график, Pine Script, Strategy Tester и [Bar Replay](https://www.tradingview.com/support/solutions/43000474024-how-do-i-turn-bar-replay-on/). Близок по пользовательскому сценарию Live/Replay; собственный серверный контракт данных команды в рамках платформы не задан.
- [TrendSpider](https://trendspider.com/product/strategy-development-and-backtesting-tools/) — визуальное построение правил, историческое тестирование и сравнение стратегий. Близок по проверке сценариев; серверная модель хранения данных продукта закрыта, поэтому технические свойства внутреннего API по открытым материалам не оцениваются.

### Косвенные аналоги

- [TimescaleDB](https://docs.timescale.com/) — расширение PostgreSQL для хранения временных рядов; решает задачу индексации и агрегации цен, но не поставляет рыночные события или правила торговой системы.
- [FRED API](https://fred.stlouisfed.org/docs/api/fred/) — источник рядов, дат публикации и ревизий макропоказателей. Решает часть задачи получения данных, но не синхронизирует их с торговыми сигналами.

**Почему выбраны критерии.** Для backend существенны: доступ к историческим и текущим данным, воспроизведение истории, возможность задать собственный контракт аналитических событий, фиксация времени доступности и происхождения данных. ### Выводы по сравнению

Прямые аналоги подтверждают востребованность исторических прогонов и подключения данных. Для собственной системы полезны разделение источника и алгоритма у LEAN, сценарий пошагового Replay у TradingView и сравнение вариантов стратегии у TrendSpider. Предметная задача проекта — связать свечи, календарь, SMC-объекты и сигналы единой временной моделью и серверным API. Утверждение о превосходстве планируемого решения над зрелыми платформами из сравнения не следует: пока это требования к прототипу, которые нужно проверить реализацией и тестами.

## 4. Итоги

**Итоговая тема ВКР:** проектирование и разработка серверной подсистемы интеграции, хранения и временной синхронизации рыночных данных для платформы анализа торговых сценариев Smart Money Concepts.

**УДК для тезиса:** 004.65 (организация баз данных); окончательный индекс согласовать с научным руководителем.

**Ключевые слова:** backend; рыночные данные; временные ряды; потоковая обработка; API; происхождение данных; экономический календарь; Smart Money Concepts; replay; бэктестинг.

### Актуальность исследования

Командный продукт объединяет данные с разной частотой и разными моментами доступности: свечи поступают по мере закрытия интервала, экономические показатели публикуются по расписанию и могут пересматриваться, а SMC-разметка и сигналы выводятся из уже полученной истории. Если сервер ориентируется только на метку времени события, исторический прогон может случайно использовать позднее опубликованные сведения и показать результат, которого нельзя было получить в тот момент. Различие времени события и обработки описано в [1], значимость точного времени макропубликации — в [5], а риск переоценки результатов тестов — в [4].

Научно-техническая проблема состоит в согласовании нескольких потоков данных для Live и Replay с сохранением происхождения каждого наблюдения. Существующие платформы дают графики, тестеры и источники, но не определяют контракт данных конкретной SMC-стратегии команды. Практическая значимость серверной подсистемы — возможность повторить расчёт, объяснить происхождение сигнала и обнаружить пропуск или ревизию данных до интерпретации результата. Работы [6]–[9] подтверждают необходимость отдельного проектирования хранения, качества и структуры исходной информации. Это не является утверждением о доходности стратегии.

### Цель исследования

Спроектировать и реализовать серверную подсистему, которая собирает, проверяет, хранит и предоставляет рыночные и макроэкономические данные аналитическим компонентам и интерфейсу в текущем и историческом режимах с воспроизводимой временной семантикой.

### Задачи исследования

1. Уточнить состав источников, доступность истории, лимиты и условия использования данных для XAUUSD, EURUSD, GBPUSD и календаря событий.
2. Разработать схему данных для свечей, публикаций, их версий, SMC-объектов, сигналов и запусков исторического расчёта.
3. Определить единые правила времени: UTC, таймфреймы, время закрытия свечи, время события, время получения и время фактической доступности записи.
4. Реализовать приём, валидацию, дедупликацию, выявление пропусков и журналирование происхождения данных; разделять исходные и восстановленные значения.
5. Реализовать хранение истории и API для выборки по инструменту, диапазону, таймфрейму и состоянию данных на момент *t*.
6. Организовать передачу подготовленных данных SMC-ядру и приём версионируемых результатов алгоритма без смешения исходных фактов и вычисленных признаков.
7. Обеспечить одинаковую семантику данных для Live, Replay и бэктестинга и регистрацию параметров каждого прогона.
8. Проверить на контрольных сценариях запоздавших событий, ревизий показателей, дубликатов и пропусков отсутствие доступа к будущим данным и повторяемость результатов.
